# EvidenceViewDB P0-A 최종 보고서

- 실행일: 2026-08-07
- 실행 방식: CPU exact inner product, GPU/LLM 미사용
- 사전등록 판정: **STOP_NO_PHYSICAL_GAIN**
- 연구 확정 판정: **현재 설계의 EvidenceViewDB를 최종 주제로 확정하지 않음**

## 1. 무엇을 먼저 확인했는가

### 1.1 신규성

원문·서지 감사 결과 다음은 이미 선행연구가 다룬다.

- 다중 해상도 증거 색인: MEGRAG, SPIRE
- 예산 아래 증거 단위 선택: MAGE-RAG, UMG-RAG
- 동적/증분 RAG 색인: MCHRAG, EraRAG
- 과제 품질 피드백에 따른 뷰·색인 물리 설계라는 상위 개념: Agentic Data Environments

따라서 EvidenceViewDB의 가능한 공백은 “다중 뷰” 자체가 아니라, **답변/증거 효용 대비 저장·갱신 비용으로 물질화 집합을 고르는 구체적 조언자와 정본 계보 유지**로 축소됐다. 이 공백은 존재 가능성이 있으나 여러 선행 요소의 결합이므로 신규성 강도는 중간이다.

### 1.2 로컬 자기 중복

기존 KIISE 연구는 이미 멀티모달 데이터에서 저장 단위, multi/dual view, 부분 색인, hot/cold 물질화의 Pareto를 측정했다. 그러므로 새 연구는 적어도 다음을 추가해야 했다.

1. 독립 전문 텍스트 도메인
2. 최소 충분 증거 또는 실제 답변 효용
3. holdout 워크로드에서 일반화되는 자동 물리 설계
4. 원문 변경의 정확한 계보 무효화

이번 P0-A는 1~3번의 선행 가능성을 검정했다.

## 2. 실험 설계

- 질의: LegalBench 776개
- 과제: ContractNLI, CUAD, MAUD, PrivacyQA 각 194개
- 대상 문서: 359개
- 후보 뷰: 고정 256자, 고정 512자, 고정 1,024자, recursive 512자
- 임베딩: 동일한 기존 4,096차원 L2 정규화 벡터
- 검색: 질의가 명시한 문서 내부 exact inner product
- 주 문맥 예산: 4,096자
- 분할: 문서 단위 60% dev / 40% holdout
- 지표: gold span coverage, evidence precision, evidence F1, 충분성(coverage ≥ 0.95)
- 저장 예산: 고정 256자 뷰 한 벌의 임베딩 크기와 동일
- 통계: 문서 클러스터 bootstrap 2,000회

입력과 사전등록, 실행 코드는 결과 전에 SHA-256으로 잠갔다. 동일 실행을 두 번 수행했고 네 산출물의 바이트가 모두 일치했다.

## 4. 핵심 결과 해석

### 4.1 “질의마다 좋은 청크가 다르다”는 전제는 맞았다

4,096자 예산에서 유일한 최적 뷰의 비율은 다음과 같다.

| 뷰 | 유일한 최적 질의 비율 |
|---|---:|
| recursive 512 | 34.54% |
| fixed 1,024 | 24.87% |
| fixed 256 | 15.98% |
| fixed 512 | 14.69% |

질의별로 정답을 알고 최적 뷰를 고르는 oracle은 holdout evidence F1 0.1709였고, 개발 분할에서 고른 단일 뷰는 0.1231이었다. 즉 선택 가능한 상한은 존재한다.

### 4.2 하지만 실제 물리 설계 조언자는 그 상한을 이용하지 못했다

개발 분할과 저장 예산만 사용한 조언자는 여러 뷰의 조합이 아니라 recursive 512 한 벌만 선택했고, 네 과제 모두 같은 뷰로 라우팅했다.

| holdout 설계 | Evidence F1 | Coverage | Precision |
|---|---:|---:|---:|
| 고정 512 기준선 | 0.1179 | 0.5339 | 0.0743 |
| 선택 설계(recursive 512) | 0.1231 | 0.5792 | 0.0770 |
| 질의별 oracle 상한 | 0.1709 | 0.7400 | 0.1093 |

선택 설계는 기준선보다 임베딩 저장 바이트가 약 94.5% 많지만 F1 차이는 +0.0052에 그쳤다. 신뢰구간이 0을 포함하고, precision 차이도 +0.0027뿐이라 사전등록한 실질 효과를 만족하지 못했다.

### 4.3 과제명만으로 라우팅하면 일반화가 불안정했다

Holdout에서 ContractNLI는 fixed 512/1,024가 recursive 512보다 좋았고, PrivacyQA는 fixed 1,024가 크게 우세했다. 그러나 개발 분할 조언자는 두 과제도 recursive 512로 골랐다. 특히 PrivacyQA는 독립 문서가 7개뿐이어서 과제 수준 선택이 불안정했다.

이 결과는 질의별 oracle을 실제 시스템 성능으로 바꾸려면 별도의 학습 가능한 라우터가 필요함을 뜻한다. 그러나 query-aware multi-granular routing은 MEGRAG·UMG-RAG 등과 가까우며, 모든 뷰를 저장하면 EvidenceViewDB의 선택적 물질화 기여가 약해진다.

### 4.4 문맥 예산을 바꿔도 결론의 핵심은 바뀌지 않았다

| 예산 | 단일 최적 뷰 | 단일 최적 평균 F1 | 질의별 oracle F1 |
|---:|---|---:|---:|
| 2,048자 | recursive 512 | 0.1741 | 0.2386 |
| 4,096자 | recursive 512 | 0.1397 | 0.1806 |
| 8,192자 | fixed 1,024 | 0.1119 | 0.1300 |

예산에 따라 단일 최적 뷰는 바뀌고 oracle 여지는 남지만, 이것만으로 저장할 복수 뷰를 사전에 고를 수 있다는 증거는 아니다. 큰 예산에서 F1이 낮아지는 현상은 gold span coverage 증가보다 불필요한 문맥 증가가 더 커 precision이 감소했기 때문이다.

## 5. 무엇이 유효하고 무엇이 기각됐는가

### 유지되는 관찰

- 전문 법률 질의에서 최적 증거 단위는 질의별로 다르다.
- 많은 문맥이 항상 좋은 것은 아니며, 문맥 예산이 커질수록 evidence precision이 낮아질 수 있다.
- 질의별 최적 선택을 예측할 수 있다면 개선 상한은 존재한다.
- 계보 기반 국소 무효화의 기본 자료구조는 현재 자산으로 구현 가능하다.

### 현재 설계에서 기각된 주장

- 과제 수준 워크로드 통계만으로 물질화할 여러 증거 뷰를 안정적으로 선택할 수 있다.
- 같은 저장 예산에서 단순 선택적 물질화가 고정 512 기준선보다 실질적으로 우수하다.
- 이번 P0만으로 답변 효용 기반 EvidenceViewDB 본실험에 진입할 근거가 충분하다.

## 6. 한계와 과장 방지

1. P0-A는 최종 답변 정확도가 아니라 span 기반 증거 효용을 측정했다.
2. 문서 발견을 제거한 문서 내부 검색이므로 전역 RAG 성능이 아니다.
3. 명제·표 행·그래프 사실 같은 새 뷰를 생성하지 않고 기존 청킹 네 종류를 사용했다.
4. 조언자는 과제 수준의 단순 라우팅이며 질의 텍스트 분류기를 포함하지 않았다.
5. G4는 행 수 기반 시뮬레이션이라 실제 재임베딩 wall-clock 이득이 아니다.

이 한계들은 더 정교한 시스템이 성공할 가능성을 남긴다. 하지만 사전등록의 역할은 가능한 모든 변형을 끝없이 시도하는 것이 아니라, **현재 제안한 연구를 확대할 충분한 증거가 있는지** 판정하는 것이다. 등록 규칙에 따라 P0-B는 실행하지 않는다.

## 7. 연구 주제 확정 권고

### 7.1 EvidenceViewDB

현재 형태로는 최종 연구 주제로 확정하지 않는다. 선행연구 중복 위험은 중간 이상이고, 선택적 물질화의 실현 가능한 이득이 첫 독립 도메인 holdout에서 임계값에 미달했다. 이 상태로 대규모 프로토타입을 만들면 “청킹 네 종류 비교 + oracle”로 보일 위험이 크며 EDBT급 데이터 관리 기여가 부족하다.

### 7.2 가능한 후속 방향

| 방향 | 현재 권고 | 이유 |
|---|---|---|
| 더 복잡한 질의별 evidence router | 주력으로는 비권고 | oracle 여지는 있으나 MEGRAG/UMG-RAG와 가까우며 복수 뷰 저장 문제를 해결하지 못함 |
| EvidenceViewDB P0-B 강행 | 금지 | 사전등록 G3 실패 |
| `FreshEvidenceDB`: 버전 일관성·삭제·수정 후 stale evidence 방지 | 별도 후보로 재설계 가능 | 검색 효용 경쟁보다 DB의 계보·원자적 버전 전환·갱신 정확성에 집중할 수 있음. 단 G4의 행 수 계산만으로는 확정 불가 |
| 완전히 다른 저장 구조 주제 | 권고 | 새 주제는 실제 update log, stale-answer 오류, 동시 질의 중 버전 일관성을 먼저 측정해야 함 |
