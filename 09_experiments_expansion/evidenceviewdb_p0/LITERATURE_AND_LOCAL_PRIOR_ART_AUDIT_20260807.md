# EvidenceViewDB 위험 선행연구·로컬 선행자산 감사

- 감사일: 2026-08-07 (Asia/Seoul)
- 목적: EvidenceViewDB를 본 연구로 확정하기 전에 신규성 과장과 로컬 기존 연구의 자기 중복을 차단한다.
- 판정 범위: 2026-08-07까지 확인 가능한 공개 원문·서지와 로컬 연구 산출물
- 판정: **넓은 제목은 중단, 좁힌 시스템 주장은 조건부 유지**

## 1. 결론

다음 세 주장은 이미 점유됐으므로 EvidenceViewDB의 신규성으로 사용할 수 없다.

1. 문장·문단·트리플 등 여러 해상도의 증거를 함께 색인한다.
2. 질의나 과제 품질에 맞추어 데이터 뷰·색인을 조정한다.
3. 동적 RAG에서 변경된 부분만 국소적으로 갱신한다.

현재 독립적인 검증 대상으로 남은 주장은 더 좁다.

> **동일한 전문 문서에서 파생된 복수 증거 뷰에 대해, 증거/답변 효용의 한계 이득을 저장 바이트·질의 지연·갱신 바이트와 함께 추정하여 실제 물질화 집합을 고르고, 정본 버전–파생 뷰–벡터–색인 엔트리 계보를 이용해 선택 집합만 정확하게 국소 갱신하는 RAG 물리 설계 조언자**

이 주장은 아직 논문으로 확인된 단일 시스템과 완전히 일치하지 않았지만, 여러 선행연구의 결합에 의존한다. 따라서 신규성은 **높음이 아니라 중간**, 연구 상태는 **CONDITIONAL GO**다.

## 3. 로컬 연구와의 자기 중복 감사

### 3.1 이미 수행된 내용

로컬 KIISE 연구에는 다음 결과가 이미 존재한다.

- `scripts/run_storage_unit_benchmark.py`: clip-caption, frame-vector, multi-vector, dual-index의 저장 단위 비교
- `manuscript/table8_dir/data/720_RESULTS_db_design_storage_index_20260713.md`: 데이터셋별 Pareto 최적 저장 단위, 전역/부분 색인, hot/cold 물질화 손익분기 분석
- `project_md/canonical/experiments/EXP04_EVIDENCE_REPRESENTATION_AND_UNIFIED_EMBEDDING.md`: 동일 인코더에서 여러 증거 표현과 검색 목표별 순위 역전, 저장·지연·품질 절충

따라서 다음 결과는 새 논문의 기여가 아니다.

- “데이터셋마다 최적 저장 단위가 다르다.”
- “다중 벡터 또는 모든 뷰 저장이 항상 좋지 않다.”
- “부분 색인이 전역 후필터보다 빠르거나 정확할 수 있다.”
- “hot/cold 워크로드에 따라 물질화 정책이 달라진다.”

### 3.2 새 연구가 반드시 추가해야 하는 것

1. 멀티모달 CCTV가 아닌 독립 전문 텍스트 도메인에서의 재현
2. qrel/검색 Recall이 아니라 최소 충분 증거 또는 실제 답변 효용과의 연결
3. 결과를 본 뒤 수작업으로 고른 표현이 아닌 holdout 워크로드 기반 조언자
4. 정본 버전과 파생 뷰의 계보, 삭제·수정 시 정확한 무효화
5. 저장 절감만이 아니라 품질–지연–갱신 비용의 공동 Pareto

이 중 2번이나 4번이 빠지면 로컬 기존 실험의 변형에 가깝고, 새 주제로 확정하면 안 된다.

## 4. 데이터와 실행 자산 감사

### 4.1 법률 도메인

`preprocessed_legalbench`에 다음 자산이 있다.

- 776개 질의: ContractNLI, CUAD, MAUD, PrivacyQA 각 194개
- 질의별 문서 경로와 span 정답
- 동일 NV-Embed 계열 4,096차원 정규화 임베딩
- 고정 256/512/1,024자 청크와 recursive 512자 청크
- 82~161개의 독립 문서가 있는 세 과제와 7개 privacy 문서

스키마 확인 결과 네 후보 뷰 모두 776개 질의의 정답 span과 겹치는 청크를 가진다. 이는 **실행 가능성 확인**일 뿐 검색 성능을 본 결과가 아니다.

### 4.2 금융 도메인

FinQA에는 500개 질의, 3,805개 청크와 임베딩이 있고 385개 질의에 usable span이 있다. 기존 실험에서 dense 검색과 oracle 사이의 답변 품질 여지가 이미 관찰됐다. 이 수치는 P0 설계 전에 알려진 정보이므로 신규 사전등록 결과로 취급하지 않는다. FinQA는 P0-A의 계보/매핑 독립 확인 및 이후 P0-B의 답변 효용 평가에 사용한다.

### 4.3 시스템

- CPU/RAM: 62 GiB RAM, 실험 시작 시 약 37 GiB 가용
- GPU: RTX 3090 2장, 감사 시점에는 유휴
- P0-A: GPU를 쓰지 않는 정확 내적 및 메타데이터 실험
- P0-B: P0-A 통과 후에만 결정론적/사람 평가를 우선하고 생성 모델을 제한적으로 사용

## 6. 중단 조건

아래 중 하나면 EvidenceViewDB를 주력 주제로 확정하지 않는다.

1. 하나의 뷰가 법률 과제 전반에서 증거 효용과 비용을 사실상 지배한다.
2. 질의별 최적 뷰 이질성은 있으나 사전에 학습 가능한 워크로드 단위로 일반화되지 않는다.
3. 저장 예산이 같은 조건에서 선택적 물질화가 단일 기준선보다 실질적으로 낫지 않다.
4. 뷰 계보의 국소 갱신이 단순 전체 재생성 대비 유의미한 비용 절감을 만들지 못한다.
5. P0-B에서 증거 효용 개선이 최종 답변 효용으로 이어지지 않는다.
