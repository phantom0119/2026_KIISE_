# EvidenceViewDB P0-A CPU 사전등록

- 고정 시각: 2026-08-07 (검색 결과 계산 전)
- 상태: **LOCKED BEFORE RETRIEVAL EVALUATION**
- 목적: 연구 주제를 확정하기 전에 다중 증거 뷰의 이질성, 선택적 물질화 이득, 계보 기반 갱신 가능성을 CPU만으로 판정한다.
- 주의: P0-A는 최종 답변 품질을 증명하지 않는다. 통과하더라도 P0-B 모델/사람 평가가 필요하다.

## 1. 사전 노출 정보

결과를 보기 전 다음 정보는 이미 알고 있었다.

- 로컬 CCTV 연구에서 저장 표현의 우열이 데이터셋과 검색 목표에 따라 달랐다.
- FinQA 500질의의 기존 실험에서 dense와 oracle 사이 답변 품질 차이가 있었다.
- LegalBench 776질의와 네 후보 뷰의 파일·임베딩이 존재한다.
- 스키마 감사에서 네 뷰 모두 각 정답 문서 안에 776/776 정답 span과 겹치는 청크가 있음을 확인했다.
- 일부 과거 LegalBench 결과 CSV가 존재한다. 본 사전등록자는 몇 개 행을 정찰했으나, 이 P0의 문서 내부 검색·고정 문맥 예산·증거 F1·holdout 물질화 결과는 계산하지 않았다.

위 정보는 독립적인 P0 결과로 보고하지 않는다.

## 2. 데이터와 고정 범위

### 2.1 주 데이터

- 질의: `mini_queries_with_gt.jsonl`의 776개 전부
- 과제: ContractNLI, CUAD, MAUD, PrivacyQA 각 194개
- 검색 범위: 질의에 명시된 하나의 대상 문서 내부
- 근거: 각 질의의 모든 `ground_truths[].span`
- 임베딩: 기존 4,096차원 L2 정규화 NV-Embed 벡터
- 유사도: 정확 내적

문서 내부 검색을 택한 이유는 P0-A가 문서 발견 능력이 아니라 **같은 원문을 어떤 물리 단위로 저장할지**를 격리해 검정하기 때문이다. 본실험에서는 전역 문서 발견을 별도 요인으로 둔다.

### 2.2 후보 증거 뷰

결과를 보기 전에 다음 네 개를 고정한다.

1. `naive_s256_o0`
2. `naive_s512_o0` — 현재 기준선
3. `naive_s1024_o0`
4. `rcts_s512_o0` — 구조 경계를 따르는 비교 뷰

Semantic 뷰는 ContractNLI/MAUD/PrivacyQA 문서를 포함하지 않아 후보에서 제외한다. overlap 뷰는 후보 수를 부풀리고 저장비가 기계적으로 늘어나므로 P0-A에서 제외한다.

## 3. 고정 검색 및 평가 규칙

### 3.1 문맥 예산

- 주 예산: 질의당 원문 4,096자
- 민감도 분석: 2,048자와 8,192자
- 점수순으로 완전한 청크를 추가하되 예산을 넘는 청크는 건너뛴다.
- 어떤 청크도 들어가지 않으면 1위 청크 하나는 포함한다.

### 3.2 span 집합 계산

- 겹치는 gold span은 합집합으로 병합한다.
- 검색 청크 구간도 합집합으로 병합한다.
- `coverage = |gold ∩ retrieved| / |gold|`
- `precision = |gold ∩ retrieved| / |retrieved|`
- `evidence_f1 = 2 × coverage × precision / (coverage + precision)`
- `hit = 1` if 교집합 길이 > 0
- `sufficient = 1` if coverage ≥ 0.95

P0-A의 주 지표는 4,096자 예산의 evidence F1이다. hit와 coverage, precision, sufficient를 함께 보고하며 F1만으로 결론을 감추지 않는다.

## 4. 분할과 물리 설계 조언자

### 4.1 분할

- seed: `20260807`
- 질의가 아니라 문서를 분할 단위로 사용한다.
- 각 과제 안에서 문서를 안정 해시 순으로 정렬하여 60% 개발 / 40% holdout으로 나눈다.
- 같은 문서의 질의는 두 분할에 섞이지 않는다.
- PrivacyQA의 문서가 7개뿐이라는 제한을 별도로 명시한다.

### 4.2 선택적 물질화

- 저장 비용은 전체 LegalBench 코퍼스의 각 뷰 임베딩 파일 바이트로 계산한다.
- 예산은 `naive_s256_o0` 한 벌의 임베딩 바이트와 동일하게 고정한다.
- 가능한 모든 비어 있지 않은 뷰 부분집합 중 예산 이하인 집합을 열거한다.
- 개발 분할에서 평균 evidence F1이 최대인 부분집합을 선택한다.
- 선택 집합 안에서 과제별로 개발 분할 평균 F1이 가장 높은 뷰를 라우팅 대상으로 고정한다.
- 동률은 저장 바이트가 작은 집합, 그다음 사전 명시 순서(512, 1024, rcts512, 256)로 해소한다.
- holdout은 선택 완료 후 한 번만 평가한다.

비교선은 다음과 같다.

1. 고정 512 뷰
2. 개발 분할에서 고른 단일 최적 뷰
3. 예산형 선택적 물질화 + 과제별 라우팅
4. 네 뷰 모두 물질화 + 질의별 oracle 라우팅(달성 불가능 상한)

## 5. 통계

- 평균 차이의 95% 신뢰구간은 문서 클러스터 bootstrap 2,000회로 계산한다.
- 과제별 결과와 전체 macro 평균을 모두 보고한다.
- PrivacyQA는 문서 수가 작으므로 신뢰구간을 탐색적으로만 해석한다.
- 여러 예산 중 주 결론은 4,096자에 한정한다. 2,048/8,192자는 방향성 확인이다.

## 6. 게이트

### G0. 실행·정합성

다음을 모두 만족해야 통과한다.

- 질의 776개와 임베딩 행 776개가 일치한다.
- 네 뷰에서 id와 임베딩 행이 일치한다.
- 네 뷰의 대상 문서에 모든 gold span과 겹치는 후보 청크가 있다.
- 동일 입력 재실행 결과가 해시 수준에서 재현된다.

### G1. 최적 뷰 이질성

4,096자 예산에서 다음을 모두 만족하면 통과한다.

- 전체 질의 중 modal best view가 차지하는 비율이 85% 미만이다.
- 최소 2개 뷰가 각각 질의의 5% 이상에서 **유일한** 최적 뷰다.

동률 허용오차는 evidence F1 `1e-9`다.

### G2. 개인화 가능 상한

- 질의별 oracle 평균 F1과 개발 분할에서 선택한 단일 최적 뷰 평균 F1의 holdout 차이가 최소 0.02
- 문서 클러스터 bootstrap 95% CI 하한이 0보다 큼

G2는 “다른 뷰가 존재한다”가 아니라 이를 선택할 가치가 있음을 판정한다.

### G3. 예산형 물질화

holdout에서 다음 둘 중 하나면 통과한다.

1. 선택적 물질화의 evidence F1이 고정 512보다 최소 0.02 높고 95% CI 하한 > 0
2. coverage 하락이 0.02 이하이면서 precision이 최소 0.10 높고 해당 차이의 95% CI 하한 > 0

개발 분할 단일 최적 뷰에 대한 차이도 숨기지 않고 보고한다.

### G4. 계보 기반 갱신 실행 가능성

- 문서의 1%, 5%, 10%가 변경되는 세 시나리오를 seed 20260807로 생성한다.
- 영향받은 문서의 선택 뷰 행을 100% 무효화하고 영향받지 않은 행을 0% 무효화해야 한다.
- 5% 변경 시 `선택 뷰의 국소 재임베딩 행 / 네 뷰 전체 재임베딩 행`이 0.50 이하이어야 한다.

G4는 국소 갱신의 구현 가능성만 확인한다. 실제 임베딩 생성시간은 본실험에서 측정한다.

## 7. 자동 판정

| 판정 | 조건 | 조치 |
|---|---|---|
| STOP_NO_HETEROGENEITY | G0 통과, G1 또는 G2 실패 | 주제 중단. 고정 저장 단위 기준선으로 충분하다고 해석 |
| STOP_NO_PHYSICAL_GAIN | G0~G2 통과, G3 실패 | 선택적 물질화 주장을 중단하거나 분류기 연구로 별도 전환 |
| STOP_LINEAGE_INFEASIBLE | G0~G3 통과, G4 실패 | 증분 유지관리 기여를 제거하고 주제 재평가 |
| CONDITIONAL_GO_TO_P0B | G0~G4 전부 통과 | 답변 효용·지연·실제 갱신을 검증하는 P0-B만 승인 |
| DATA_FAILURE | G0 실패 | 연구 가설이 아니라 데이터/파이프라인 실패로 판정 후 수정 등록 |

## 8. 금지 해석

- P0-A 통과를 “답변 정확도 향상”으로 표현하지 않는다.
- 문서 내부 검색 결과를 전역 RAG 검색 결과로 일반화하지 않는다.
- 질의별 oracle을 실제 시스템 성능으로 보고하지 않는다.
- 갱신 행 수 계산을 실제 wall-clock 갱신 성능으로 바꾸어 말하지 않는다.
- P0-A 결과를 본 뒤 이 문서의 임계값을 바꾸지 않는다.

## 9. P0-B 진입 시 필수 항목

1. FinQA와 법률 도메인에서 결정론적 정답 지표 또는 사람 이중 주석 사용
2. 고정 512, 전체 물질화, MEGRAG/SPIRE류 온라인 다중 단위 기준선과 비교
3. answer utility, p50/p95 지연, 저장 바이트, 실제 재임베딩 시간 공동 측정
4. 수정·삭제·버전 충돌에서 stale evidence 0건 검증
5. 결과를 보기 전 별도 P0-B 사전등록
